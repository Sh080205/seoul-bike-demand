หน้า 1 · ปก 0:10

สวัสดีครับ กลุ่มเราทำโปรเจกต์ Seoul Bike Demand คือทายว่าแต่ละชั่วโมงจะมีคนเช่าจักรยานในโซลกี่คัน จากพยากรณ์อากาศและปฏิทินครับ

หน้า 2 · โจทย์ + เมตริก 0:40

ข้อมูลมาจาก UCI มี 8,760 ชั่วโมง ตั้งแต่ ธ.ค. 2017 ถึง พ.ย. 2018 เป้าหมายคือยอดเช่าคันต่อชั่วโมงของทั้งเมือง จึงเป็น regression และเราใช้แค่ข้อมูลที่รู้ล่วงหน้าได้ ไม่ใช้ยอดเช่าชั่วโมงก่อนหน้า

กราฟนี้คือยอดเช่าใน train เบ้ขวา ค่าเฉลี่ย 756.8 สูงกว่ามัธยฐาน 582.5 เราเลยใช้ MAE เป็นเมตริกหลัก เพราะอ่านตรงว่าทายคลาดเฉลี่ยกี่คัน และไม่ถูกชั่วโมงพีคไม่กี่ชั่วโมงครอบงำแบบ RMSE

หน้า 3 · Split ตามวัน 0:45

ความท้าทายแรกคือการแบ่งข้อมูล ชั่วโมงในวันเดียวกันคล้ายกันมาก ถ้าสุ่มทีละชั่วโมง 14:00 อาจอยู่ train แต่ 15:00 อยู่ test โมเดลก็แค่จำวันนั้น เราเลยแบ่งทีละวันด้วย GroupShuffleSplit โดยใช้วันที่เป็น groups

รอให้โค้ดพิมพ์จบ แล้วชี้ groups=df["date"]

ได้ train 292 วัน test 73 วัน และบันทึกรายการวันลงไฟล์ ทุก notebook ใช้วัน test ชุดเดียวกัน test มีครบ 4 ฤดู แต่มีฤดูหนาวมากกว่า train ซึ่งเราจะกลับมาพูดตอนดูผล test

หน้า 4 · EDA 0:50

EDA ทำบน train เท่านั้น เจอ 3 อย่างที่เปลี่ยนการออกแบบ อย่างแรก วันทำงานมี 2 พีค คือ 8 โมงเช้าประมาณ 1,381 คัน และ 6 โมงเย็นประมาณ 1,810 คัน ส่วนวันหยุดไม่มีพีคเช้า

อย่างที่สอง อุณหภูมิเป็นโค้งคว่ำ ยอดสูงสุดช่วง 25–30 องศา อย่างที่สาม ชั่วโมงที่มีฝน ยอดเฉลี่ยตกจาก 795 เหลือ 164 คัน ไม่ว่าฝนมากหรือน้อย ความสัมพันธ์ที่ไม่เป็นเส้นตรงพวกนี้คือเหตุผลที่โมเดลต้นไม้ชนะในตอนท้ายครับ

ส่งต่อ: "ต่อไป [ชื่อผู้พูด B] จะเล่าการเตรียมข้อมูลครับ"

หน้า 12 · สรุป 0:30

สรุป โมเดลสุดท้ายคือ HistGradientBoosting ได้ test MAE 97.4 คันต่อชั่วโมง R² 0.919 ดีกว่าการใช้เวลาอย่างเดียวประมาณ 73% และเรากันข้อมูลรั่วตลอดทางด้วย split ตามวัน Pipeline และ GroupKFold

ข้อจำกัดคือชั่วโมงฝนตกและเหตุการณ์พิเศษที่ไม่มีในข้อมูล ถ้าทำต่อจะเพิ่มข้อมูลหลายปีและ feature เทศกาลกับคำเตือนอากาศ ขอบคุณครับ ยินดีรับคำถามครับ

ผู้พูด B — หน้า 5–7 · เตรียมข้อมูล, Pipeline, คัดฟีเจอร์

หน้า 5 · เตรียมข้อมูล 0:40

ผมจะเล่าการเตรียมข้อมูลครับ ชั่วโมงที่ระบบปิดมี 240 แถวใน train และยอดเป็น 0 ทุกแถว เราตัดออกและประกาศว่าโมเดลใช้กับชั่วโมงที่ระบบเปิดเท่านั้น

ความชื้น 0% มี 17 แถว เราคำนวณย้อนกลับจากอุณหภูมิกับ dew point ด้วยสูตร Magnus ได้ 33 ถึง 72% แปลว่าเซนเซอร์ผิด จึงแปลงเป็น NaN แล้วให้ Pipeline เติมด้วย median ส่วน outlier อื่นเป็นเหตุการณ์จริง เราไม่ตัด และเพิ่ม feature ใหม่ 7 ตัว เช่น hour_sin, hour_cos, is_raining

หน้า 6 · Pipeline + GroupKFold 0:45

ความท้าทายที่สองคือข้อมูลรั่วระหว่าง cross-validation เราใส่ imputer, scaler และ one-hot ไว้ใน Pipeline ทุกครั้งที่ CV จะ fit ใหม่บน training fold เท่านั้น

ชี้ groups=groups_train ในโค้ด แล้วชี้แผนภาพ fold

และใช้ GroupKFold ให้ทั้งวันอยู่ fold เดียวกัน วันซ้ำระหว่าง train กับ validation เป็น 0 ทุก fold ถ้าใช้ KFold ธรรมดา validation 281 วันจะซ้ำกับ train ทั้ง 281 วันครับ

หน้า 7 · คัดฟีเจอร์ + PCA 0:40

เราทำ feature selection ครบ 3 แบบ คือ Filter, RFE และ Lasso ใช้ chi² ไม่ได้เพราะ target ต่อเนื่อง ผลคือ RFE ใช้แค่ 30 จาก 58 คอลัมน์ได้ MAE เท่าเดิม แต่ไม่มีวิธีไหนทำให้ดีขึ้นเกินระดับ noise เราจึงใช้ทุก feature

PCA ต้องใช้ 14 component ถึงจะได้ 90% ของ variance และช่วย kNN ได้เล็กน้อย จาก 194.4 เหลือ 189.5

ส่งต่อ: "ต่อไป [ชื่อผู้พูด C] จะเล่าการเทียบโมเดลครับ"

ผู้พูด C — หน้า 8–11 · โมเดล, tuning, test, ทำนายข้อมูลใหม่

หน้า 8 · เทียบ 4 โมเดล 0:45

เราเทียบ 4 ตระกูลโมเดลด้วย 5-fold GroupKFold baseline ที่ใช้แค่ชั่วโมงกับประเภทวันได้ MAE 401 ทุกโมเดลชนะ แปลว่าข้อมูลอากาศช่วยจริง

HistGradientBoosting ดีที่สุดที่ 114.1 ส่วน gap ระหว่าง train กับ validation บอกว่า Random Forest overfit ที่สุด gap 85.6 และ Linear Regression underfit gap แค่ 6.4 เพราะจับความโค้งกับ interaction ไม่ได้

หน้า 9 · Tuning + เลือกโมเดล 0:30

tune ด้วย CV บน train เท่านั้น HGB ดีขึ้นเป็น 109.0 ห่าง Random Forest 12.8 คัน ประมาณ 1.5 เท่าของ std เราจึงเลือก HGB ส่วนเวลา fit และเวลาทำนายเร็วพอใช้งานจริงทุกตัว

หน้า 10 · ผล test ครั้งเดียว 0:40

หลังเลือกโมเดลแล้ว เราเปิด test ครั้งเดียว ได้ MAE 97.4 RMSE 170.1 R² 0.919 ใกล้กับ CV แปลว่าไม่ overfit ที่ต่ำกว่า CV เพราะ test มีฤดูหนาว 31.5% ซึ่งยอดต่ำ ไม่ได้แปลว่าโมเดลเก่งขึ้น

จุดอ่อนที่สุดคือชั่วโมงฝนตก คลาด 88.7% ของยอด

หน้า 11 · ทำนายข้อมูลใหม่ 0:45

ขั้นสุดท้ายคือทำนายข้อมูลใหม่ ข้อมูลดิบผ่าน add_features ตัวเดียวกับตอนฝึก แล้วเข้า final_model ซึ่งรวม preprocessing ไว้ในตัว

พุธ 6 โมงเย็นอากาศดี ทาย 2,981 คัน ถ้าฝนตก 3 มม. เหลือ 204 วันเสาร์เวลาเดียวกัน 2,167 และเช้าฤดูหนาว 690 ทิศทางทุกปัจจัยตรงกับที่เห็นใน EDA ครับ

ถาม-ตอบ → สไลด์สำรอง 1–5

สไลด์สำรองอยู่ต่อจากหน้า 12 เรียงตามคำถามที่น่าจะโดนถามมากสุดก่อน · กด → ไล่ไปทีละหน้า หรือกด B เลือกจากเมนู · หัวสไลด์แต่ละหน้าบอกว่าตอบคำถามอะไร · คนที่ตอบคือคนที่พูดหน้านั้นในช่วงนำเสนอ

สำรอง 1 · พิสูจน์ว่าไม่รั่ว ตอบ: B

ถ้าถาม: "รู้ได้ไงว่าไม่มีข้อมูลรั่ว"

เราตรวจ 2 ชั้นครับ ชั้นแรกคือ GroupKFold ตารางนี้นับวันที่ซ้ำกันระหว่าง train กับ validation ได้ 0 ทุก fold ถ้าใช้ KFold ธรรมดา validation ของ fold 0 มี 281 วัน และซ้ำกับ train ครบทั้ง 281 วัน

ชั้นที่สองคือ Pipeline ค่าเฉลี่ย temp_c ที่ scaler เรียนได้เปลี่ยนไปตาม fold ตั้งแต่ 13.348 ถึง 13.395 แปลว่า fit ใหม่บน training fold ทุกครั้ง ไม่เคยเห็นข้อมูล validation ด้านล่างเป็นเช็คลิสต์ เช่น target ไม่อยู่ใน X และเราแตะ test ครั้งเดียวในขั้น 13

สำรอง 2 · ตารางโมเดลเต็ม + MSE ตอบ: C

ถ้าถาม: "ทำไมไม่ใช้ accuracy" · "MSE อยู่ไหน" · "ทำไม test MAE ต่ำกว่า CV"

accuracy ใช้กับ classification ครับ งานเราเป็น regression จึงรายงานครบ 4 ตัว คือ MAE, MSE, RMSE และ R² ของทุกโมเดลในตารางนี้ MSE มีหน่วยเป็นคันยกกำลังสอง อ่านยาก เราจึงอธิบายด้วย RMSE ซึ่งเป็นรากที่สองของมัน ทุกเมตริกเรียงอันดับเหมือนกัน HGB ดีที่สุดทุกตัว

ส่วน test ได้ MAE 97.4 ต่ำกว่า CV 109.0 เพราะ test มีชั่วโมงฤดูหนาว 31.5% ส่วน train มี 22.9% ฤดูหนาวยอดเช่าต่ำ ค่าคลาดเป็นจำนวนคันจึงเล็กตาม ไม่ได้แปลว่าโมเดลเก่งขึ้นครับ

สำรอง 3 · Feature selection ละเอียด ตอบ: B

ถ้าถาม: "RFE / Lasso ตัด feature อะไรบ้าง" · "ทำไมใช้ทุก feature"

Filter ทั้ง f_regression และ mutual_info ยิ่งเก็บ feature มาก MAE ยิ่งดี ดีสุดตอนใช้ครบ 58 คอลัมน์ที่ 266.2 ส่วน RFE ใช้แค่ 30 คอลัมน์ได้ 265.8 แทบเท่าเดิม แปลว่าอีก 28 คอลัมน์ซ้ำซ้อน

Lasso ที่ alpha 0.1 ให้ coefficient เป็น 0 จำนวน 6 คอลัมน์ คือบางวันในสัปดาห์ บางเดือน และ seasons_Summer ส่วน coefficient ใหญ่สุดเป็นชั่วโมง เช่น 18:00 บวก 836.8 ไม่มีวิธีไหนลด MAE ได้เกินระดับ noise เราจึงใช้ทุก feature ส่วน PCA ช่วย kNN เล็กน้อยจาก 194.4 เหลือ 189.5 ที่ 15 component แต่ทำให้ Linear แย่ลงครับ

สำรอง 4 · 10 ชั่วโมงที่ทายพลาดมากที่สุด ตอบ: C

ถ้าถาม: "ชั่วโมงไหนทายพลาดหนักที่สุด" · "โมเดลพลาดเพราะอะไร"

5 ใน 10 แถวมาจากวันเดียว คือ 23 ส.ค. 2018 ช่วง 18 ถึง 22 นาฬิกา เป็นวันที่ไต้ฝุ่น Soulik ขึ้นฝั่งเกาหลีใต้และโรงเรียนปิด แต่อากาศที่วัดได้ดูปกติ ฝนเกือบเป็น 0 โมเดลจึงทายสูงเหมือนวันทำงานทั่วไป เช่น 3 ทุ่ม ยอดจริง 189 คัน แต่ทาย 1,613 คัน

อีกแถวคือ 24 ก.ย. ซึ่งตรงกับวันชูซอก dataset ไม่มี feature เหตุการณ์พิเศษ ถ้าทำต่อจะเพิ่มคำเตือนอากาศกับวันเทศกาลครับ

สำรอง 5 · Correlation + outlier ตอบ: A

ถ้าถาม: "จัดการ outlier ยังไง" · "feature ไหนสัมพันธ์กับยอดมากสุด"

เราตรวจ outlier ด้วยกฎ IQR บน train เช่น ฝนนับได้ 413 ชั่วโมง หรือ 6.10% แต่ฝนกับหิมะมี IQR เป็น 0 เพราะเกือบทุกชั่วโมงไม่มีฝน ทุกชั่วโมงที่มีฝนจึงถูกนับเป็น outlier ทั้งที่เป็นเหตุการณ์จริง เราจึงเก็บไว้ ไม่ตัดออก

ส่วน correlation ยอดเช่าสัมพันธ์กับอุณหภูมิมากที่สุด r เท่ากับ 0.55 รองลงมาคือชั่วโมง 0.44 ครับ
